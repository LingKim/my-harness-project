## 2. 使用方法

### 2.1 勾选规则

- `[ ]`：未开始或尚无可验证结果。
- `[x]`：已经完成，并且存在可追溯的设计、代码、测试输出或验收记录。
- 一项任务只有在“产物已落盘 + 对应验证通过”后才能勾选，不能因为代码已写但未测试而勾选。
- 每完成一个功能，当天更新本计划和对应 OpenSpec `tasks.md`；本计划记录模块进度，OpenSpec 记录具体变更证据。
- 任务被取消时不直接删除，改为 `~~任务~~（取消：原因）`，保留决策记录。
- 需求或范围发生变化时，先更新 PRD/OpenSpec，再同步本计划，不能只改计划表。

### 2.2 完成定义（Definition of Done）

一个功能只有同时满足以下条件，才算完成：

- [ ] 需求和验收场景已经确认，没有未解决的关键歧义。
- [ ] 交互、数据、API、权限、异常和降级方案已经设计。
- [ ] 前端、后端、数据库或内容任务按实际范围完成。
- [ ] 新增或变更行为有自动化测试，且测试真实运行通过。
- [ ] 涉及用户主流程时，完成真实浏览器端到端验证。
- [ ] 中英文、权限、安全、隐私和无障碍要求已按功能复核。
- [ ] 文档、实现和配置一致，没有调试代码、占位实现或无关改动。
- [ ] 相关子仓库验证通过，根仓库 `./scripts/check-harness.sh` 通过。

### 2.3 单人开发限制

- 同一时间只允许 1 个业务功能处于“开发中”，减少上下文切换和半成品堆积。
- 每周预留约 20% 时间处理测试、缺陷、文档和技术债，不把全部工时排成功能编码。
- AI 可以协助检索代码、拆任务、生成测试、实现小步变更和代码评审，但开发者必须确认需求、审查差异并运行验证。
- 外部 AI、对象存储、翻译等服务必须保留可替换边界，禁止把开发环境密钥提交到仓库。
- P0 闭环未通过前，不并行扩展 P2、更多城市、更多语种或完整移动端能力。

## 4. 20 周里程碑计划

本排期按每周 5 个工作日估算，并包含单人开发所需的评审、返工和测试缓冲。外部服务采购、内容翻译和用户招募若不能及时完成，里程碑应顺延，不压缩安全与测试时间。

| 阶段 | 周期 | 主要目标 | 退出条件 |
| --- | --- | --- | --- |
| P0：需求与总体设计 | 第 1—2 周 | 关闭 PRD 决策，冻结页面、领域、数据库、API、安全和测试基线 | M00 全部勾选；首批 OpenSpec change 获确认 |
| P1：应用骨架与账号 | 第 3—5 周 | 完成官网框架、双语基础、认证和旅行上下文 | M02、M03 达到完成定义 |
| P2：攻略与文本 AI | 第 6—8 周 | 完成结构化攻略、受控检索和文本问答最小闭环 | 可从攻略或首页发起 AI 问题并获得有依据答案 |
| P3：社区与 v0.1 | 第 9—11 周 | 完成社区问答、解决反馈和 v0.1 全链路 | v0.1 P0 主流程 E2E 通过 |
| P4：现场问题增强 | 第 12—14 周 | 完成图片提问、会话转社区、通知和攻略反馈 | v0.2 主流程 E2E 通过 |
| P5：运营与质量闭环 | 第 15—17 周 | 完成运营后台、举报治理、翻译、高风险路由和质量观察 | v0.3 运营闭环验收通过 |
| P6：上线准备与试运行 | 第 18—20 周 | 完成内容、安全、性能、兼容性、部署和小范围试运行 | M10、M11 全部上线门禁通过 |

## 6. 每周执行模板

每周只承诺能够在本周内完成并验证的小任务。复制下面模板到周记录或对应 change 的 `tasks.md`：

```markdown
## 第 N 周：本周目标

### 本周承诺

- [ ] 任务 ID：任务说明
  - 产物：精确文件、页面、接口或 migration
  - 验证：精确命令或浏览器场景
  - 验收：可观察结果

### 周末复核

- [ ] 已更新 OpenSpec tasks 和本开发计划。
- [ ] 已记录实际运行的测试命令与结果。
- [ ] 未完成任务已说明原因并重新排期。
- [ ] 下周只有一个主要开发目标。
```

### AI Coding 单功能循环

1. 开发者选择本计划中的一个任务，确认需求编号、边界和验收结果。
2. 使用 `/opsx:propose` 创建或补全对应 change；规格确认后才使用 `/opsx:apply`。
3. AI 先读取真实代码、局部规则和相关 Skill，再提出最小实现步骤。
4. 能自动化的行为先写失败测试，确认失败原因正确后实现最少代码。
5. 运行相关测试、静态检查和必要的真实浏览器验证。
6. 开发者审查差异、安全、权限、错误路径和无关改动。
7. 更新 change 的 `tasks.md`，再勾选本计划对应项；未验证的任务不勾选。
8. 完成一个 change 后同步规格并归档，再选择下一个任务。

## 7. 风险、缓冲与调整规则

| 风险 | 计划影响 | 调整方式 |
| --- | --- | --- |
| PRD 决策未关闭 | 数据库和 API 无法稳定设计 | 暂停业务编码，只推进不依赖该决策的原型或测试设计 |
| 单人并行任务过多 | 半成品增加，回归成本升高 | 强制单功能 WIP；新需求进入待办，不直接插队 |
| AI/图片服务不稳定 | 阻塞问答或上传联调 | 使用可控 fake 完成自动化测试，真实服务另设集成门禁 |
| 双语内容供给慢 | 攻略不能发布，AI 知识不足 | 内容从第 6 周开始同步生产，不等代码全部完成后再准备 |
| 社区冷启动 | 无法验证社区解决率 | 上线前准备种子问题/回答和明确的贡献者来源 |
| AI 安全评测不达标 | 不满足上线条件 | 缩小问题范围、加强升级和拒答，不以删减测试换取上线 |
| 任务实际工时超出 | 20 周里程碑顺延 | 优先保 P0 闭环，P1 后移；不把 P2 混入 MVP |

排期调整原则：P0 需求和安全门禁不删减；优先延后 P1 运营体验，再延后非核心视觉优化。任何延期都应更新本表的周期、原因和新验收日期。
