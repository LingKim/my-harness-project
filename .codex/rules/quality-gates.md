# 质量门禁

## RULE-QA-001：验证与变更风险相称

- 规格场景必须有实现和自动化测试；无法自动化时记录原因和手工验证证据。
- 选择最接近变更的静态检查、单元测试、集成测试或真实场景；默认不运行无关 build，不等于可以跳过相关测试。
- 文档和治理变更至少运行对应治理检查、`git diff --check` 和 OpenSpec strict validate。

## RULE-QA-002：三个仓库分别验证

- 前端按局部 conventions 选择 lint、typecheck、Vitest 和 Playwright；后端按局部 conventions 选择架构测试、业务测试和数据库集成验证。
- 根级 Harness 验证仓库编排和治理接入，不替代前端/后端测试、真实运行或数据库证据。
- 跨仓库变更分别记录每个仓库实际执行的命令和结果。

## RULE-QA-003：完成声明必须可追溯

- 没有本轮新的验证输出不得声称“已修复”“已完成”或“可运行”。
- 交付前检查调试代码、占位实现、静默吞错、无关格式化、文档漂移和工作区范围。
- 明确区分通过、失败、未运行和受环境阻塞的验证项。

## RULE-QA-004：证据记录可复核的最小结果

- 每项自动化验证记录执行时间、仓库、执行角色、完整命令、`PASS`/`FAIL`/`BLOCKED`/`NOT_RUN` 状态和关键输出摘要。
- 手工或真实场景记录环境、操作、期望、实际、状态和相对证据路径；未运行或受阻时记录原因、影响和后续处理。
- task checkbox、计划命令和主观推测不是验证证据；没有实际输出不得补写为 `PASS`。
- QA、Spec Reviewer 和 Experience Reviewer 返回结构化结果，主 Agent 负责将适用内容持久化到 change；只读 Reviewer 不因报告落盘而获得写权限。
