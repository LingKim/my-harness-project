# OpenSpec 与实现工作流

## RULE-WF-001：非平凡行为规格先行

- 新功能、行为变化、架构调整、跨文件修复和治理契约变化必须先探索需求并建立 OpenSpec change。
- proposal、specs、design 和 tasks 必须完整，且在用户确认规格前不得进入实现。
- 纯文案、注释和无行为变化的机械格式化可以直接处理，但仍需验证实际差异。

## RULE-WF-002：实现按小任务和证据推进

- 每个任务必须说明目标文件、预期结果和验证方式；有依赖的任务串行，互不依赖且不争用文件的任务才可并行。
- 能自动化的行为遵循 RED → GREEN → REFACTOR；实现揭示规格错误时先更新 artifacts 再继续。
- 每完成一个 OpenSpec task 立即更新 checkbox，状态不能只留在聊天记录。

## RULE-WF-003：验证、同步和归档有明确门禁

- 实现完成后检查规格符合性、回归、安全、可维护性、文档一致性和无关改动。
- 只有 tasks 全部完成、验证通过且 delta/main specs 同步后才可归档。
- 实际命令、结果和未验证项必须如实报告；网络、权限或环境失败不能伪装成规格失败或成功。
